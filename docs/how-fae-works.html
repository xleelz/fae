How Fae works

Fae ("Crook") is a local-first orchestration daemon that drives AI coding agents through a durable, evidence-gated software workflow: specification, a failing RED test, implementation, reviews, QA, a reviewed-byte commit and serialized integration. This page models its data, its execution, its architecture and its command line, built from the source tree.

Data models: how workflows and tasks are defined

A workflow is a named, versioned JSON document. Each revision is immutable and append-only (latest+1, parent = latest). A task is admitted against exactly one revision and keeps it for life. The executing instance of one revision is called a molecule. In the running daemon the molecule is not a separate row: each task's engine.Job pins the full document, its workflow_hash and revision, and every dispatch id embeds that hash. Everything about a task lives in one jobs row whose payload is {admission, job}, saved with an atomic Dolt commit.

Architecture: from the operating system to the task state machine

Fae is one singleton daemon per instance (fae serve) that owns a private Dolt database, an authenticated Unix-socket API, a drive loop, a pure engine, host-wide admission, isolated agent sessions and an allowlisted effects broker. The tabs below go from the processes and files on the host, through the executor's contract with a running session, to the exact task state machine.

4

The CLI data model

fae is one binary. serve starts the daemon; almost every other verb is a typed RPC over <home>/<instance>/run/rpc.sock, authenticated with the instance's owner credential. Every mutation must cite a recorded operator message (--authorizing-message) whose class matches the action. Pick a verb to see its flags, the RPC it sends, the authorization it needs and what it returns.
