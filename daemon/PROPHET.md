# Prophet sessions

`fae prophet chat --task ID --text TEXT` queues a bounded, asynchronous turn and returns its message ID. `fae prophet session --task ID --after N --limit 100` reads durable chat pages and task context; `fae prophet global --text TEXT` queues an instance liaison turn, and `fae prophet global --after N` reads its conversation. Replies identify the original message in `reply_to`. Each entry has an author, daemon-recorded time and monotonic per-scope sequence. Chat reads report queued/completed/failed turns; old daemon queued turns are explicitly interrupted and never automatically replayed.

Per-task prompts contain only the pinned task workflow, a bounded content excerpt, the latest 100 evidence/history/context entries with explicit history and artifact offsets/counts, disposition, that task's most recent 100 chat entries, and the latest 50 operator messages scoped to the task (`fae message --task ID`, replies in such threads inherit the task; each text is cut at 8 KiB and marked `truncated`, with `operator_messages_total` giving the full count) (FAE-OPS-030). Global prompts contain compact task summaries and daemon health, plus the latest 100 molecule identities/revisions and 20 persisted alerts with explicit overflow flags. The task list makes no whole-table read (FAE-CP-009) and holds at most 1,000 summaries and 512 KiB; `tasks_total` counts the drive's tasks and those finished before the daemon started (from startup's per-state counts, as Status counts them), and `tasks_truncated` says the list was cut. The drive's tasks come first, unfinished before finished, each in id order, from the daemon's published snapshot with no plane read and no writer lock: task, state, workflow, revision, a 1 KiB content excerpt and reason, disposition and history event count. Tasks finished before the daemon started follow in id order, marked `finished_before_start`, with task, state, workflow, revision and reason only: from the finished-task summary once built (READS.md), else paged from their job and task columns only as far as the list has room. A per-task session reads the rest of such a task. Quarantined tasks appear in the health section. Read pages are capped at 2 MiB and turn context is limited to 1 MiB, chat input to 64 KiB, and output to 1 MiB with bounded reply/action fields. Larger histories must be inspected through paging; an oversized context fails before launch rather than silently losing task evidence.

The live path runs a fresh, handoff-only ordinary provider session through the existing weighted host and Herdr (`herdr-core`) pane admission/reaping machinery. Its empty workflow role table cannot acquire any workflow role slots. The bridge receives a private empty directory, no configured repository files, no tool capabilities, and no resumable provider context. The binding is configured with `serve --prophet-provider` (default `claude`) and `--prophet-model` (default `claude-opus-5-5`). `--prophet-routes FILE` optionally supplies an ordered JSON array of up to eight unique provider/model bindings (with optional effort); when absent the fixed flags remain the default. Routes share the durable workflow provider-health rows and structured log classifier. Every attempt selects the first eligible remaining route, persists its typed outcome, and confirms process retirement and lease release before any failover. `--prophet-max-failovers` defaults to one (zero selects that default), accepts 1..7, and -1 disables failover. Invalid output, including an answer the bridge refused, is classified as malformed; pre-provider failures, including a turn the bridge refused before the provider ran, do not penalize provider health. A provider that never acknowledged the prompt (`provider-not-started`) follows the workflow's agent-start rule (FAE-RT-004): it is relaunched on the same route, each start after confirmed retirement and charging nothing, up to three starts; the start that exhausts the bound records `unavailable` against that binding and fails over within the failover budget (one failover per route, not per start). A provider that failed after acknowledging (`provider-failed`) is classified from its log like any failed turn. Unreadable health, uncertain observation persistence, or unconfirmed cleanup fail closed. If all routes are unhealthy the conversation records a failed reply without launching; a new explicit operator message is required after recovery. Failed or interrupted chats are never automatically replayed. Conversation continuity comes from durable plane messages rather than an opaque provider memory. Tests can install a trusted scripted `Config.ProphetRunner` to inspect the exact scoped brief.

Proposals are text only. To allow an action, the operator explicitly supplies `--direct RestartWithInformation` or `--direct ResumeWithContext`; a global command additionally requires `--action-task ID`. Only those two actions are allowed, and the generated action must match the exact structured operator scope. The daemon records the structured directing message, then invokes the existing task-control implementation as actor `prophet`, citing that message. Unsupported, undirected or cross-task actions produce a refused reply. No Prophet can approve code, waive a gate, alter governance, create a quality disposition, or submit operator messages through delegated credentials.

Chat submission returns before provider execution; poll pages for the response. A chat reserves its scope's slot (one turn per task, one global, eight in all) under the writer lock and makes its plane I/O (reading its scope, then writing the queued message, turn marker and chat entry) without it, so another mutation never waits for them (FAE-ROB-021); a failure frees the slot. Route observations take no writer lock either. A turn's reply rows, and an action it enacts, are recorded under the writer lock, and the slot is freed in the same hold, so a chat sent once a reply shows never finds its scope busy nor misses that reply. Runtime cancellation/restart preserves the request and conservatively reports interruption; no automatic re-execution of a potentially acted-on request occurs. A reply checkpoint failure is logged and the durable queued record remains an unresolved outcome. Transcript storage currently uses immutable blob-backed plane marker entries and is not physically compacted. Only messages explicitly scoped to the task are enumerated; unscoped messages and other tasks' messages are never included, so a broad grant shared across tasks cannot leak into a task's context. Prophet chat directions are recorded on a separate `prophet` channel and appear only as chat entries. A Prophet-directed restart is covered by `TestProphetContextOperatorMessagesAndDirectedRestart`.
