# Command policy

Supported Go build/test/vet and gofmt host-command vectors pass the existing literal broker allowlist, then command policy, before process launch under the caller's durable heavy lease. Go package and test concurrency are capped at two, and at one for a whole-suite test run (FAE-HOST-015): recursive targets, and no `-run` or a last `-run` that selects every test. A `-run` selects every test when, split as the testing package splits it (alternatives at `|`, subtest levels at `/`), one alternative's top-level pattern compiles and matches each of a fixed set of test function names chosen to be unlike each other (`Test` alone, digits, underscores, upper-case ASCII and non-ASCII letters, a title-case letter, ideographs, a long name; `goTestNameProbes`, `goTestRunSelectsEveryTest`); so `-run=`, `-run=.*`, `-run=Test.*`, `-run='(X|.*)'`, `-run=T` and `-run=.*/Sub` run at one thread and `-run=TestX` and `-run='^Test[A-Z]'` (which misses `Test_x`) at two. A pattern that matches every probe but misses some real test name only puts a nearly whole run at one thread; each brokered run is also capped at 512 tasks (cgroup v2 `pids.max` through a transient systemd user scope, `effects/process_limit.go`; live config `process_limit`, `-1` disables; a host without pids delegation degrades to `prlimit` with RLIMIT_NPROC at the user's task count plus 512, logged, and only a host where neither works runs uncapped); Go flags with tool execution, overlays, external targets, or unknown semantics are refused. Formatter trees are bounded to 10,000 entries / 64 MiB and expanded to explicit Go files; individual files must be at most 1 MiB / 30,000 lines. Symlink escapes and RAM-temporary output paths are refused. VCS operations use the dedicated VCS broker: this policy refuses every git vector in every mode as an ordinary refusal, since it is not a version-control shim; the role's shims and the nested git wrappers have the distinct Local code below.

Every Direct/Herdr (`herdr-core`) role session gets private PATH-first wrappers (`role.go`, FAE-HOST-011) for go, gofmt, cargo, rustc, rustfmt, make, cmake, ninja, pytest and git. When the daemon runs as the `fae` binary with a host ledger, each wrapper execs `fae heavy-op run --shim-policy <session>/command-shims/.policy.json -- NAME ARGS...`. The policy records the session's worktree, mode, the role's build/test/format grants from its tool profile, each real tool resolved from the session's base PATH at install time (so a wrapper never finds itself) and, when that go sits in a GOROOT, the session's GOROOT mirror (below). The broker then:

- refuses `git push` and `git remote` (and push's plumbing, `git send-pack` and `git http-push`) in Local mode with 78 and the reason (FAE-MODE-002), ahead of the refusals below, so the code holds when the profile's shims omit git or the call is nested; the subcommand is found past git's global options (`git -C DIR push`, `git -c NAME=VALUE push`);
- refuses with 77 and the reason, before requesting any lease: pre-code roles (no grant) for any build, test or formatter call; a working directory or target outside the own worktree; a RAM-backed `-o`; unsupported Go verbs, flags and probes; every build wrapper without a scoped adapter; every other git command (roles have no VCS; the engine's VCS broker commits); a tool missing from the base PATH; and any shim call inside an already brokered command (`FAE_SHIM_NESTED`, FAE-HOST-014). The nested marker grants nothing; stripping it only queues the nested call for its own lease;
- runs the prepared, clamped vector (`-p=2 -parallel=2`, whole suite 1) under a role-class heavy-op lease of Appendix A weight (whole suite or recursive build 2, otherwise 1), re-validating paths under the granted lease, with `GOFLAGS` cleared, `GOENV=off`, `GOTOOLCHAIN=local`, `GOROOT` set to the session's mirror when it has one, and every `FAE_HEAVY_OP_*` marker stripped; lease and host refusals exit 75, otherwise the command's own code. A go or gofmt that the role's test starts therefore meets the session's wrappers and is refused as a nested call.

Without a broker (a non-`fae` executable such as a test binary) or ledger, the wrappers are the refusal stubs below; a Local session's are `InstallLocalDenials` (`local_denials.go`), whose git exits 78 with the Local-mode reason for a push or remote change (`push`, `remote`, `send-pack`, `http-push`, found past git's global options as `RunShim` finds them) and 77 for every other call. Claude Code or Codex provider processes get `InstallDenials` wrappers that return 77. Host-command child processes get them too by default (refuse mode), `InstallLocalDenials` for a Local task's run (or one whose context names no task): a nested build never gets an implicit free resource slot. Operator-declared unknown command vectors remain trusted, literal-allowlisted host effects; they are not a sandbox.

PATH-first wrappers alone miss the commonest nested call. `go test`, `go run` and `go generate` start their programs with `$GOROOT/bin` first on PATH (cmd/go's `base.AppendPATH`), so a `go` or `gofmt` a Go test starts would find the real toolchain ahead of any wrapper. A brokered command and a role session therefore run go under a GOROOT mirror (`goroot.go`, `InstallGoRoot`): a private directory beside the wrappers with a symlink to every entry of the real GOROOT except `bin/`, whose `go` and `gofmt` are the wrappers and whose other tools link to the real ones. The real GOROOT is found as go finds it (`GoRoot`: the environment's `GOROOT`, else two or three directories up from the go binary, as given and through symlinks); with no go on the PATH there is no mirror, and none when the go binary sits outside any GOROOT (a version manager's shim script, or a copy relying on its built-in GOROOT), where a test's own go still reaches the real toolchain, neither refused nor accounted. That gap is reported (`GoRootGap`): the daemon logs it at start as a `component=host` line of its supervision log, and `fae doctor` warns (`go-toolchain:goroot`). Runs still run without a mirror rather than fail closed: failing would refuse every Go run on such a host for a gap the operator closes by putting a go that sits in its GOROOT (or a symlink to one) first on the daemon's PATH, or by setting `GOROOT` in each HostCommand stage's `environment`. The command runs with `GOROOT` set to the mirror, `GOTOOLCHAIN=local` (a switched toolchain would put its own `bin/` first again, so a module that needs a newer Go fails with go's own message) and `GOENV=off` (no Go env file adds flags), so `$GOROOT/bin`, `go env GOROOT` and `runtime.GOROOT()` all lead to the wrappers. The real toolchain does the work, and the build cache is shared: go keys a compiled package without GOROOT's path, so nothing is recompiled under a mirror. Only linking is keyed by it, so a nested `go build` of a binary relinks once in each run (a test binary is linked on every run anyway). A broker that runs inside another run's tests (Fae's own suite) finds the outer mirror's `go` first and mirrors that mirror, so its wrappers come first and its calls pass the outer wrappers too. The broker seals a run's mirror and its `bin/` read-only once it is made (`SealGoRoot`), so the command cannot add, replace or rename an entry by mistake, the wrappers' links among them, and removes it with the run's policy directory (`scratchfs.RemoveAll`, which first makes every directory of the tree writable, so a sealed mirror goes too), as the daemon's start sweep does for a killed run's. A role session's mirror is removed when the session ends; the session directory and its logs are kept. The mirror is not containment: the command runs as its owner and can make it writable again, and a test can still run `$(go env GOROOT)/pkg/tool/...` or an absolute path to another go.

FAE-HOST-014 lets a nested build or test pass through the same shim and be accounted under the parent's lease instead of being refused. Refusal is the default; accounting is opt-in per instance (live config `nested_commands: "account"`, `effects.Broker.NestedCommands`). It needs the `fae` executable, which applies the policy (`effects.Broker.NestedBroker`); the daemon refuses account mode at setup when it runs as anything else, such as a test binary. A brokered host command's children then get `InstallAccounting` wrappers (`accounting.go`) for the same tools, beside the run's policy (`.policy.json`: the run's worktree, its on-disk TMPDIR, whether the task is Local, each real tool, resolved at install time from the run's base PATH, excluding the wrapper directory, with go and gofmt taken from the real GOROOT's `bin/` first, and the run's Go setting: its GOROOT mirror and its own values of the Go environment a nested go may keep but not change, its build locations among them). Each wrapper is a short `/bin/sh` script that:

- writes one record file of its own (the working directory, tool name and arguments, NUL-separated) into a records directory the broker creates beside the wrappers. The file name is the wrapper's PID and a sequence number, created exclusively. Its modification time is the call's time;
- then execs `fae --home DIR heavy-op run --shim-policy <policy> -- NAME ARGS...` (`--home` so the broker never needs the caller's `$HOME`). `RunShim` sees an accounted policy, applies `Policy.PrepareAccounted` and execs the tool in its own place with the caller's environment (for go, adjusted as below), so the call's exit code is the tool's.

`PrepareAccounted` is the command policy for nested calls. Its scope is the run's worktree and its TMPDIR, where tests keep their fixtures, and, for go and gofmt, `/var/tmp` when it is on disk (`AccountedTemp`): test suites keep fixtures there that need short paths, such as Unix sockets, and Fae's own daemon and CLI tests build and test inside them, so a scope without it refused Fae's own suite once its nested go reached the policy. The RAM-backed roots of nested calls are `/tmp` and `/dev/shm`, and `/var/tmp` only when it is a RAM file system (tmpfs or ramfs):

- `go build`, `go test`, `go vet` and `go list` must run from inside the scope and get Prepare's clamp: `-p=2` (with `-parallel=2` for test), or 1 for a whole-suite test run (FAE-HOST-015): recursive targets, and no `-run` (or `-test.run`) or a last one that selects every test, as above. A `-test.run` after `-args` counts too, since the test binary takes it after go test's own; a `-run` in `GOFLAGS` and a `-skip` are not counted as filters, so such a run keeps one thread. A target is recursive when it has `...` or is one of go's reserved patterns (`all`, `std`, `cmd`, `work`, `tool`), so an unfiltered nested `go test all` runs one package and one test at a time. The call's own `-p`, `-parallel` and `-test.parallel` are dropped wherever they appear, after `-args` too, and `-cpu` (or `-test.cpu`, in `GOFLAGS` or after `-args` too) may list no value above the call's clamp, as the top-level policy never runs a test at more threads. Path targets must resolve inside the scope. Import-path targets (`github.com/x/y/cmd/z`, `std`) are left to go, so a test can build its module's binaries.
- Their flags are an allowlist (`nestedGoFlags`), applied to the arguments and to `GOFLAGS`, which is split as go splits it (quoted fields included). After `-args`, go hands the arguments to the test binary without reading them: there a `-test.` flag must be one that writes no file (`nestedGoTestBinaryFlags`: `-test.run`, `-test.v`, `-test.count`, `-test.timeout` and the like), so the profile and output flags (`-test.coverprofile`, `-test.outputdir`, ...), which go test's own forms before `-args` give with their paths checked, go test's plumbing (`-test.gocoverdir`, `-test.testlogfile`, ...) and unknown `-test.` flags are refused; the test's own flags and anything after a `--` pass. Listed are go's build flags except `-C`, `-toolexec`, `-gccgoflags` and `-linkshared`; go test's flags except `-exec`, also with their `test.` prefix; go list's; and go vet's except `-vettool`, with its analyzers' flags. Any other flag, such as a test's own `-update` before `-args`, is refused. Every path-valued flag (`-o`, `-pkgdir`, `-outputdir`, `-overlay`, `-modfile`, `-reuse`, `-pgo` unless `auto` or `off`, the `-debug-*` traces, and the test profiles `-coverprofile`, `-cpuprofile`, `-memprofile`, `-blockprofile`, `-mutexprofile` and `-trace`, relative to `-outputdir`) must resolve inside the scope and never under a RAM-backed root (FAE-HOST-020). `-gcflags`, `-ldflags` and `-asmflags` may pass only listed compiler, linker and assembler flags (`nestedGoToolFlags`: such as `-N -l -m` and `-s -w -X -buildid -linkmode`; not the compiler's `-d` debug settings), so none runs another program (`-extld`, `-extar`, `-extldflags`, and the linker's `-I` and `-r`, which name the dynamic linker and library path a built binary, a test binary too, starts with) or writes a file (`-o`, `-tmpdir`, `-asmhdr`, `-json`, the profiles). `-compiler` must be `gc` and `-buildmode` is never `shared`; `-linkmode=external` and the build modes that link externally (`c-shared`, `plugin`, ...) run the run's own C compiler, which the environment check below keeps. A stage's `GOFLAGS` reaches nested builds when every flag in it is listed, and the clamp's explicit flags override any parallelism it sets.
- A nested go runs with the run's Go setting (`accountedGoEnv`): `GOROOT` the run's mirror, or a mirror a broker inside the run made of it; `GOTOOLCHAIN=local`; `GOENV=off`. Each is set when the call has none (or an empty one), so a test that clears its child's environment still gets them, and a call that names another GOROOT, toolchain or Go env file is refused. For `go build`, `test`, `vet` and `list`, a Go build location (`GOCACHE`, `GOMODCACHE`, `GOPATH`, `GOTMPDIR`, `GOCOVERDIR`, `TMPDIR`) under a RAM-backed root outside the scope, or a `GOWORK` file outside the scope, is refused unless it is the run's own setting. The rest of the call's Go environment is an allowlist (`nestedGoEnv`, from `go help environment`), checked for every verb and every entry of a repeated key. A call may set freely only what changes the build's target (`GOOS`, `GOARCH` and their levels, `GOEXPERIMENT`, `GOFIPS140`, `CGO_ENABLED`, `GO_EXTLINK_ENABLED`), where modules come from (`GO111MODULE`, `GOPROXY`, `GONOPROXY`, `GOPRIVATE`, `GONOSUMDB`, `GOSUMDB`, `GOINSECURE`; a direct fetch runs git through its wrapper), `GOBIN` (written only by `go install`, a refused verb), the runtime's settings (`GODEBUG`, `GOGC`, `GOMEMLIMIT`, `GOTRACEBACK`) and the `CGO_*FLAGS_DISALLOW` patterns. Every other `GO*` and `CGO_*` key keeps the run's own value (the broker records the run's, `NestedGoKeptEnv`) or stays unset for go's default: the programs go and cgo run (`CC`, `CXX`, `FC`, `AR`, `GCCGO`, `GCCGOTOOLDIR`, `PKG_CONFIG`, `GOCACHEPROG`, `GOAUTH` but `off`, `GOVCS`), the C compiler's and linker's flags, which can name programs and plugins (`CGO_CFLAGS`, `CGO_CPPFLAGS`, `CGO_CXXFLAGS`, `CGO_FFLAGS`, `CGO_LDFLAGS` and the `_ALLOW` patterns that let `#cgo` lines pass such flags), `GORACE` (whose `log_path` writes anywhere) and any key the policy does not know. `GOMAXPROCS` may also be at most the call's clamp.
- The programs go finds by name for cgo are the run's own (`accountedCgoPrograms`). go looks up the C compiler (`gcc`, or `clang` for a darwin or BSD target), the C++ compiler, `gfortran` and `pkg-config` on its PATH when `CC`, `CXX`, `FC` or `PKG_CONFIG` is unset or names a program without a directory, and a nested call's PATH is the test's. The broker records where the run's own PATH finds each (`NestedGoPrograms`, `NestedGo.Programs`), and a nested call (any verb but `go version`, which runs no C toolchain) has the variable set to that absolute path, keeping the arguments of the run's own value; a call it starts may keep the pinned value. When the call's PATH has none of a program, the variable stays unset, so go still turns cgo off on a host without a C compiler. When the call's PATH has a program the run's PATH does not, the call is refused. A nested cgo build therefore runs the host's compiler, never a `gcc` a test puts first on its PATH (`TestBrokerNestedCgoBuildRunsTheRunsCompiler`). Cgo is not refused: nested `go test -race` and nested builds of Fae itself need it. Not pinned: the programs those programs find on PATH themselves (the assembler and linker gcc runs, `ar` for `-buildmode=c-archive`), version control tools go runs, `go_GOOS_GOARCH_exec` for a cross-compiled test, and the C toolchain's and the dynamic loader's own variables (`COMPILER_PATH`, `GCC_EXEC_PREFIX`, `LD_PRELOAD`): a test can run any program on its PATH itself.
- `go version` and `go env` are read-only probes and run as called, from anywhere; `go env -w` and `-u` are refused. Every other go verb is refused (`go run`, `go mod`, `go generate`, `go tool`, `go install`).
- `gofmt` gets the formatter limits (FAE-HOST-012) inside the scope.
- `git` (`accounted_git.go`, FAE-MODE-002, FAE-EXT-001, FAE-VCS-002, FAE-VCS-010) asks the real git which repository the call uses, with the call's working directory, global options (`-C`, `--git-dir`, `--work-tree`, `--bare`, `-c`) and environment (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_INDEX_FILE`), and decides by where that repository's common and own git directories, object directory, index and work tree are. A task worktree is a linked worktree of the operator's repository: it shares that repository's refs, objects, configuration and hooks, and every other task's worktree is registered there.
  - A repository that lies entirely in the run's TMPDIR, nested in its worktree, or in `/tmp`, `/var/tmp` or `/dev/shm`, and is not the run's own, is changed as called: tests commit, branch and configure their own repositories there. Its git directories (common and own) and object directory may hold no symbolic link git would write through to anywhere else, and its configuration may keep its references nowhere else (`extensions.refStorage` with a path): a test repository whose `.git/refs` or `.git/worktrees` linked into the operator's let `update-ref` move the operator's `main` and `worktree remove` delete another task's worktree (`checkRepositoryLinks`; loose objects and packs are not read, since git only adds them as new files; a repository with more than 20,000 other entries to read is refused).
  - The run's own repository (the operator's) and any repository elsewhere, such as the checkout a self-hosting clone came from, may only be read: `status`, `diff`, `log`, `show`, `rev-parse`, `rev-list`, `ls-files`, `ls-tree`, `cat-file`, `for-each-ref`, `show-ref`, `merge-base`, `describe`, `blame`, `grep` and a few more, `config` reads, `branch` and `tag` listings, `worktree list` and a `symbolic-ref` read, none naming a file to write (`--output`, which every command that takes revision or diff options accepts, `rev-list` and `blame` included). The call runs with `--no-optional-locks`, so even `git status` leaves the index alone. A `-c` or `--config-env` setting is refused there unless it is harmless (`log.showsignature`, which Go's VCS stamping passes; `core.fsmonitor=false` and `core.hooksPath=/dev/null`, which Fae's own git calls pass; `user.*`, `color.*`, `advice.*`, `core.quotepath`, `core.abbrev`, `safe.directory`), and so are `GIT_CONFIG`, a `GIT_CONFIG_COUNT` setting outside that list, and a `GIT_CONFIG_GLOBAL` or `GIT_CONFIG_SYSTEM` other than `/dev/null`. Every other call there exits 77, or 78 when a Local task changes a remote (a `remote.*` or `url.*` configuration write).
  - `git init` and `git clone` must create their repository (and any `--separate-git-dir`) where a call may change one, and `init` may not reinitialize a protected repository, which would copy its template's hooks into it. A `config` write to a named file (`--file`, `--global`, `--system`, `GIT_CONFIG`) must write there too, and so must every file a call names for git to write (`writeTargets`): `--output` on any subcommand, `format-patch -o` and the `format.outputDirectory` it uses without one (from `-c`, a named file or the repository's own configuration), `archive -o`, `bundle create`'s file, `index-pack -o` and the pack it indexes, `pack-objects`' base name, `fast-export` and `fast-import` marks and pack edges, `mailsplit -o`, `mailinfo`'s files, `interpret-trailers --in-place`'s files, `merge-file`'s first file, `checkout-index --prefix`, and the `--object-dir` of `commit-graph` and `multi-pack-index`; `apply --unsafe-paths` exits 77. `worktree add` and `move` must put the worktree there, and the worktrees `remove`, `move` and `repair` change must lie there and not belong to the run's own repository. `repair` changes more than the paths it names: `.` when it names none, and always the `.git` file of every worktree its repository lists (each `.git/worktrees/<id>/gitdir`, absolute or relative; `accountedGitListedWorktrees`), so each listed worktree is checked as a named one is. A bare `git worktree repair` in a test repository whose `.git/worktrees/x/gitdir` named another task's worktree used to point that worktree's `.git` file at the test repository. A worktree whose `.git` file names no valid repository (what `repair` mends) belongs to the run's own repository when that file names a git directory inside the run's. Every path a call names is checked as the system takes it when git creates and writes it (`accountedGitResolve`), component by component and never cleaned as text: an existing component is followed through its symbolic links; a component that does not exist yet is the directory git creates there (`mkdir -p`, as `init`, `clone`, `format-patch -o` and `worktree add` do) or the file it writes; a `..` leads up from where the previous component lies, from where a link points or from the real parent of a directory git would create; and a component that exists but cannot be followed (a link leading nowhere, a loop, a file where a directory is needed) is refused, since `open` creates the file a dangling link names. Cleaned as text, `scratch/l/../config`, with `l` a link to the operator's `.git/refs`, was checked as `scratch/config`, and `git bundle create scratch/l/../config HEAD` overwrote the operator's `.git/config` (wave 12); handing the rest to the text cleaner from the first missing component, `scratch/n1/../l/../PWN` was checked as `scratch/PWN` while git created `n1`, followed `l` and created the operator's `.git/PWN`, and `format-patch -o scratch/nn/../l/../hooks` wrote a patch into the operator's `.git/hooks` (re-audit 11); and `log --output=scratch/dl`, with `dl` a link to a name inside the operator's `.git`, was checked as the link while `open` created that file. The check is of the path as it is when the policy runs: a link planted or switched between the check and the exec is the race below.
  - Everywhere, a push or remote change (`push`, `remote`, `send-pack`, `http-push`, found past git's global options) exits 78 for a Local task and 77 for any other: external effects go through the daemon's effect grants. (So a nested `go` that fetches a module straight from version control, with `GOPROXY=direct` or for a private module, fails at its `git remote add`, as it did before.) Mail and foreign-VCS commands (`imap-send`, `send-email`, `svn`, `p4`, ...), server and transport commands (`daemon`, `receive-pack`, `upload-pack`, ...), credential helpers, `subtree`, and any subcommand the policy does not know, which covers git aliases (`git -c alias.p=push p`) and `git-*` programs on PATH, exit 77. So do `maintenance start` and `register`, `--exec-path=DIR`, a global option git does not have, an argument naming a path inside the run's own git directory, and a call whose repository git cannot report.
  - Everywhere, on a test's own repository too, 77 refuses what the call itself gives git that names a program for git to run (FAE-MODE-002, FAE-EXT-001):
    - options and subcommands: `submodule foreach`, `rebase --exec`, `bisect run`, `--upload-pack` (and `ls-remote`'s `--exec`), `archive --exec`, `grep --open-files-in-pager`, `init --template` and `clone --template` (they copy a directory's hooks and configuration, which can name programs, into the new repository), `difftool`, `mergetool`, `filter-branch`, and a merge, pull, rebase, cherry-pick or revert strategy git does not have (`-s NAME` runs `git-merge-NAME` from PATH);
    - settings from `-c`, `--config-env`, `GIT_CONFIG_COUNT` and `clone --config` (`accountedGitChosenSetting`, built from git-config(1) for git 2.55): every key whose name is `*.cmd`, `*.command`, `*.program`, `*.textconv`, `*.driver`, `*.helper`, `*.path` (a tool's path, or `include.path` and `includeIf.*.path`, which load a file of settings), `core.sshCommand`, `core.askPass`, `core.gitProxy`, `core.editor`, `sequence.editor`, `core.pager` and `pager.*`, `diff.external`, `remote.*.uploadpack`, `receivepack` and `vcs`, the browsers, `interactive.diffFilter`, `init.templateDir`, `uploadpack.packObjectsHook`, `gc.recentObjectsHook`, `imap.tunnel` and `sendemail.smtpServer`; every `filter.*` key; `core.hooksPath` other than `/dev/null`; every `hook.*` key but `hook.<event>.enabled` or `hook.<name>.enabled` set to false (a hook's `command`, `event`, `enabled=true`, `jobs`, `parallel`); `core.fsmonitor` other than false; `submodule.*.update=!...`; and a `pull.twohead` or `pull.octopus` naming a strategy git does not have. An empty value names nothing (except for `core.hooksPath` and `hook.*`), nor do `:` and `true` for an editor, or `cat` and a boolean for a pager. `fetch.bundleURI` and `transfer.bundleURI` are refused too, since git downloads bundles over HTTP. The same settings are refused in a global or system file the call names (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`: the file is configuration the call chose; a relative name, or a file git cannot read as configuration, is refused too), and in a nested `git config` write on any repository (`refuseProgram`), as is a section rename, which can turn harmless settings into such ones; a bundle setting is written, since every call switches bundles off over any file (below);
    - variables: `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_EXTERNAL_DIFF`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `EDITOR` and `VISUAL` (other than `:` or `true`), `GIT_PAGER` and `PAGER` (other than `cat`), and `GIT_CONFIG_PARAMETERS`, which the policy does not read (set configuration with `-c` or `GIT_CONFIG_COUNT`); and every other `GIT_*` variable the policy does not know (`accountedGitKnownEnv`). That is an allowlist, as for nested go, from git(1), git-config(1) and the names git 2.55 reads: a call may set identities and dates, where the repository is (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_CEILING_DIRECTORIES`, ...; the policy finds the repository with them in effect), pathspec, replace-ref, notes, merge and progress behaviour, HTTP settings nested calls never reach, and the configuration and trace variables above. Git keeps adding variables that run a program or write a file: `GIT_TEST_FSMONITOR=PROGRAM git status` in the task worktree ran the program, which planted a branch in the operator's repository, and `GIT_REFERENCE_BACKEND` keeps references at any path;
    - a `GIT_TRACE*` variable that sends git's trace to a socket, or to a file or directory outside the places a call may change: a trace appends to the file it names.
  - Nested git reaches only local repositories (FAE-GEN-010). A repository the call names by a URL that is not a path or `file://` exits 77: a `scheme://` URL, a remote helper's `TRANSPORT::ADDRESS` or ssh's `HOST:PATH`, named by `clone` (or its `--bundle-uri`), `fetch` (each of `--multiple`'s), `pull`, `ls-remote`, `archive --remote` or `submodule add`. A remote named by its name, a `url.<base>.insteadOf` rewrite and a submodule's URL meet git's own protocol list instead: every call runs with `GIT_ALLOW_PROTOCOL=file` (below), so git refuses any other transport with `fatal: transport 'https' not allowed` (exit 128), whatever `protocol.*.allow` says.
- Every other tool (cargo, make, pytest and the rest) is refused with 77, as Prepare refuses it.

Every call the policy passes runs the real git with `accountedGitExecEnv`, the call's environment (each key once, at its last value) with:

- `GIT_CONFIG_GLOBAL=/dev/null` unless the call names a global file, and `GIT_CONFIG_NOSYSTEM=1` unless it names a system one, as the broker's own environment sets them. A `HOME` or `XDG_CONFIG_HOME` the call points elsewhere, after dropping those variables, therefore loads no configuration on any repository; the `rev-parse` the policy runs to find the repository loads no global or system file either. (`HOME` and `XDG_CONFIG_HOME` still choose git's default ignore and attributes files, which name no program.) A `git config --global` write with no `GIT_CONFIG_GLOBAL` of its own fails with git's `could not lock config file /dev/null`, as it does in any brokered command that keeps the broker's environment; a test names its global file with `GIT_CONFIG_GLOBAL`.
- `GIT_ALLOW_PROTOCOL=file`: git reaches only paths and `file://` URLs. This also lets a submodule clone a local repository, which git's own default leaves to a call the user makes.
- `GIT_TRACE2`, `GIT_TRACE2_PERF` and `GIT_TRACE2_EVENT` set to `0` unless the call sets them (a target it sets is checked as above): git also reads those targets from a global or system file (`trace2.eventTarget`), where a set variable outranks the file. A named global file's `trace2.eventTarget` appended JSON to the operator's `.git/config`, after which every git call there failed.
- `core.hooksPath=/dev/null`, `hook.<event>.enabled=false` for every event of githooks(5) (the list matches git 2.56.0's), `core.fsmonitor=false`, `fetch.bundleURI` empty and `transfer.bundleURI=false`, as `GIT_CONFIG_COUNT` settings after the call's own, which outrank every configuration file. git reads a call's `-c` and `--config-env` settings after `GIT_CONFIG_COUNT`, though, so those settings alone do not hold: a call's own `-c hook.pre-commit.enabled=true` outranked the forced false and ran a pre-commit hook the test repository's configuration named, which moved the operator's `main` (re-audit 10's probe). The policy therefore refuses, from every source a call sets configuration with (above), each `hook.*` setting but one that switches a hook off, and `core.hooksPath` other than `/dev/null`. With both, no hook (from a hooks directory or a configured `hook.<name>.command`) or file-system monitor runs on a nested call that passes the policy, whoever installed it: a hook runs the real git, past the wrappers, and one installed by a nested `git config core.hooksPath` moved the operator's `main`. A test's own repository's hooks therefore do not run under account mode (no Fae test relies on one). Nor does git download bundles over HTTP past its protocol list. They show in `git config --list`.

A call on a repository runs pinned to it (`pinned`): `-C` its canonical working directory (followed as `chdir` follows it, through a link before a later `..`), then its other global options, then `--git-dir` and `--work-tree` the canonical git directory and work tree the policy checked, in place of the `-C`, `--git-dir` and `--work-tree` it gave. A call in a bare repository or inside a git directory keeps git's own discovery from its canonical working directory unless it named its git directory (`--git-dir`, `--bare`, `GIT_DIR`). A symbolic link the call named, switched to the operator's repository between the check and the exec, no longer redirects it (re-audit 9's swap won 25 of 150 races). Programs git starts see `GIT_DIR` and `GIT_WORK_TREE` set, as they would after an explicit `--git-dir`.

A refusal exits 77 (78 for a Local push or remote change) with the reason on stderr, and the real tool never runs. No accounted call takes a lease of its own. It runs inside the parent run's lease window, in its process group and under its task cap (FAE-HOST-015), and is retired with the run. The lease bounds the run's weight, not the number of nested calls it makes at once. Nothing else bounds them but the task cap: each call is clamped, but a test that starts nested calls from several goroutines runs them all at once (`-parallel=1` bounds the tests running at a time, not the goroutines inside one). Bounding concurrent nested calls is an open operator decision. Every value the broker writes into a script is single-quoted and every expansion double-quoted, so a call's arguments and working directory are never evaluated. Only shell builtins run before the exec, so an empty PATH still records. A tool missing from the base PATH is recorded and then fails with 127 and a message. A call whose record cannot be written is refused with 77, so no call runs unrecorded. A refused call is recorded too. After the command exits, `ReadAccounted` gives the exact count and the first 16 calls in time order, each bounded to 16 arguments of 256 bytes and a 512-byte directory.

Account mode applies its policy to what reaches the wrappers; it does not contain the command. The command runs as the same user, so it can rewrite the records and the policy file, run a tool by absolute path (`/usr/bin/git push`) or reset PATH. What a nested git call can still reach:

- Programs a test's own repository's configuration names when the test wrote that configuration itself, not through a nested `git config` (a filter or diff driver, an editor, a file remote's `upload-pack`, `gpg`), run as the test set them up. A read of a protected repository still runs that repository's own configured programs (a diff driver); hooks and the file-system monitor run on neither.
- Programs git finds by name on the call's PATH are not checked (`gpg` when `verify-commit` or `log --show-signature` reads a signed commit, `ssh-keygen` for SSH signatures), on a read of a protected repository too.
- A test's submodules are not checked: a submodule whose `.git` file the test points at another repository's git directory is changed through it. A file in a test repository's `.git` hard-linked to one of the operator's is written in place (git appends to reflogs).
- The checks and the exec are separate steps. A concurrent process that changes things between them is not seen: one that renames a directory on the canonical path, plants a link in the repository's `.git`, rewrites its configuration or a named configuration file, or swaps a file the call names for git to write. `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY` and `GIT_COMMON_DIR` are checked where they lead when the policy runs. The window is wide: re-audit 10 ran a loop toggling a test repository's `.git/refs` between a directory and a link to the operator's `.git/refs`, and 36 of 150 `update-ref` calls through the wrapper created refs in the operator's repository (re-audit 9 measured 25 of 150). The pinned exec closes only a swap of a path the call named; the link walk sees only a link present while it runs.

Programs git itself starts never reach the wrappers, since git puts its own directory first on their PATH, so their own git calls run the real git unchecked; they inherit `GIT_ALLOW_PROTOCOL=file` unless they reset it. Giving git a helper directory whose `git` is the wrapper, as the GOROOT mirror does for go, was measured and not built: across the worktree, controller and effects suites git started 348 git subprocesses of its own beside 6,891 calls the tests made (about 5% more calls through the policy, at about 8 ms each), but every one of those would then pass the policy too, carrying the parent's `-c` settings in `GIT_CONFIG_PARAMETERS` (Fae's own `worktree add` passes `-c core.hooksPath=/dev/null`, so its internal `branch` and `reset` would), running plumbing such as `pack-objects --stdout` in a protected repository a fetch reads, and calling internal helpers (`submodule--helper`) the policy does not know, on the path of every self-hosted engine run. The records are evidence of what passed through the wrappers.

`hook.go` is the pre-tool predicate against an absolute-path or PATH-reset bypass: `fae heavy-op hook --shim-dir DIR` reads one provider pre-tool request (`{"tool_input":{"command":...}}`) and prints a `PreToolUse` deny decision when the command names a shimmed tool by a path outside the session's wrapper directory or may reset the PATH lookup the wrappers rely on. Each word is read as the shell reads it: quoting and escapes are removed, so `/usr/bin/g''o`, `/usr/bin/g\o` and `/usr/bin/$'\x67o'` all name `go`; a backslash-newline is joined first; and brace lists and letter sequences are expanded, so `{/usr/bin/go,build}` and `/usr/bin/{f..h}o` name it too (a numeric sequence is left as written, and an expansion past 1,024 words is denied unchecked). The PATH resets it denies are:

- any word `PATH` or `PATH=` assignment, and likewise `BASH_ENV` (a file every non-interactive bash sources);
- `env` named by any path (`/usr/bin/env`) with any option, before its first operand, that clears the environment (`-i`, `-`, clustered as in `-iv`, `--ignore-environment` or a GNU abbreviation such as `--ignore-env`), unsets PATH (`-u PATH`, `-uPATH`, `--unset=PATH`) or takes the search path or a login class's environment from elsewhere (BSD `-P`, `-L`, `-U`); options with a value are skipped with it (`env -C / -i`), and a `-S` string is read as further env arguments;
- `exec -c` (an empty environment), `exec -l` or `exec -a -NAME` (a login shell), and `command -p` (the default PATH);
- a shell started as a login or interactive shell or with an rc file (`bash -l`, `-lc`, `-i`, `--login`, `--rcfile`, `--init-file`), which reads profiles that can reset PATH;
- sourcing a file: `.` or `source` as a command (after assignments, redirections and prefixes such as `builtin` or `if`, or opening a shell's `-c` string). A sourced file can reset PATH (`/etc/environment`) or put its own tools first (a Python virtualenv's `activate` puts its `pytest` ahead of the shim), and the check cannot see its contents, so every sourcing is denied.

It also denies these ways around the shims that need no PATH reset:

- a git or cargo dashed subcommand run as a command, by name or by path (`git-push`, `~/.cargo/bin/cargo-clippy`), or named by path in git's exec directory anywhere in the line (`xargs /usr/lib/git-core/git-push`). It skips the git shim and its Local push refusal. A file that only starts with `git-` and is not a command (`cat docs/git-notes`, `git-hooks.sh`) passes;
- a Go toolchain internal by path, `.../pkg/tool/GOOS_GOARCH/NAME` (`$GOROOT/pkg/tool/linux_amd64/compile`), which skips the go shim's clamp; `go tool compile` goes through the shim;
- a shimmed tool run as a command under another fixed name: a Go toolchain as `go1.N` or `gotip` (`go1.22.0 build`, `~/go/bin/gotip test`), which runs that toolchain's `go` by path and skips the go shim's clamp; pytest as a Python module (`python -m pytest`, `python3 -Bm pytest`, `python -m py.test`) or under its other names (`py.test`, `pytest-3`, `py.test-3`), which skips the pytest shim's refusal; and `rustup run` (`rustup run stable cargo build`), which puts a toolchain's `cargo`, `rustc` and `rustfmt` ahead of their shims. Like the dashed subcommands these are checked where a command starts, so a tag or text that only names them (`git checkout go1.22.0`, `grep "python -m pytest"`) passes, and so does one started by another program (`nice go1.22.0 build`, `xargs python -m pytest`, `xargs py.test`);
- `systemd-run` in any position (`systemd-run --user -P go build .`), which runs its command under the service manager, with the manager's PATH and outside the session's process tree.

It is a lexical, over-inclusive check over shell words, not a sandbox. These pass:

- a tool name or option built by an expansion it cannot evaluate (`/usr/bin/$x`, `env $flag`, a glob, `eval "$cmd"`, `$(go env GOTOOLDIR)/compile`);
- a tool run under another name, from a copy or link made where the check cannot see it (`./g push`);
- programs that run their command as another user or on another host, with a PATH of their own: `sudo` (its `secure_path`), `su`, `doas`, `pkexec`, `run0` and `ssh`. The provider's own permission rules govern changing user or host;
- programs that hand a command to another process manager, which runs it outside the session's process tree and often with that manager's PATH instead of the session's: `tmux` or `screen` sending it to a server that is already running (`tmux new -d 'go build'`), `at` and `batch`, `crontab`, `systemctl --user start` of a unit, and `docker run` or `podman run` (a container's own tools). `systemd-run` is the one such program the hook denies;
- programs that put their own tools ahead of the shims before running a command: `uv run`, `poetry run`, `pipenv run`, `conda run` and `nix-shell --run` (`uv run pytest` runs the environment's pytest). Sourcing an environment's `activate` is denied, as above;
- a shell that reads profiles of its own accord (zsh's `.zshenv`);
- an interpreter that execs a tool itself (`python -c`, `perl -e`), and a tool started by another program rather than from the command line (`xargs go1.22.0`);
- a compiler or build tool that is not a shimmed tool: `gccgo`, `tinygo` (`tinygo test ./...` builds and runs Go tests with its own compiler), `gcc` or `clang`. The hook checks only the shimmed names (`go`, `gofmt`, `cargo`, `rustc`, `rustfmt`, `make`, `cmake`, `ninja`, `pytest`, `git`) and the other names of them above.

The hook exits 0 with the decision on stdout; any failure (a usage error, an unreadable request, no `$HOME`, a decision it cannot write, standard output closed, discarded on `/dev/null` or a pipe its reader has closed) exits 2, which a provider pre-tool hook treats as "block" (fail closed). It never exits 1, on which the provider would run the tool, and a closed pipe never kills it with SIGPIPE. The shipped bridges still disable all command tools, so no provider configuration registers it yet.

Supported bridges apply the configured tool permissions and pre-tool hooks; interpreter-based build/test tools use separate HostCommand stages. PATH wrappers alone cannot prevent a hostile arbitrary bridge or a trusted command from executing absolute binaries, resetting PATH, or forking directly. Other provider tool integrations require a real pre-tool enforcement boundary before enabling command tools. Scoped Cargo/rustfmt, pytest/Python/Ruff, and TypeScript/Node adapters are described in [language support](../docs/language-support.md). External build wrappers and formatter dialects without an adapter remain unsupported and fail closed.

`guard.go` is a production Gobra proof target for admission conjunction only; native tests cover path measurement and actual wrapper execution. The Gomela model abstracts lease return after nested refusal and process retirement; it does not model account mode, whose calls take no lease and are retired with the run's process group, and it is not an OS containment proof.

`heavyop.go` is the hidden broker verb `fae heavy-op run --weight N --class role|controller|operator [--ledger DIR] [--max-wait D] -- COMMAND...` (FAE-CLI-053; `--max-wait` defaults to 30 minutes). It admits through the host admission it shares with `fae gate run`, landing and the controller roll build (`controller.HeavyAdmission`): the hard breaker refuses at once; soft pressure backs off, for a role-class run (every shim run) at most the policy's 10 re-checks at 3 s and then refuses (FAE-HOST-002, -005), and for a controller- or operator-class run until `--max-wait`, as landing and `gate run` wait; the two-reading I/O gate passes before the lease is requested (FAE-HOST-010), so a fresh broker waits at least 30 s; it then queues FIFO on the host ledger (`--ledger`, `$FAE_HOST_LEDGER`, else the host-stable `~/.fae/host-ledger`; a missing ledger is refused, never provisioned), reclaiming proven-dead owners' entries on every access (FAE-HOST-031); one reading under the granted lease must still be clear. Its waits are recorded on standard error in the supervision log's line form (FAE-OBS-001): an RFC 3339 UTC timestamp, `instance=` (the instance whose alert spool the shim policy names, else `--instance`) and `component=heavy-op`, then the pool's waiting event for a lease wait, and in the controller's reading form (FAE-HOST-005) the reading that starts a hold, the one that lifts it, a timeout's and a hard refusal's. They go to standard error only, not to the instance's log file. Under the default policy a role-class soft-pressure hold cannot lift within the 10 re-checks, so the record is the first held reading and the timeout's. The command runs with every `FAE_HEAVY_OP_*` permit marker stripped and with parent-death SIGKILL; the lease is released after exit and the command's own code returned. Any refusal exits 75, distinct from the shim's 77, and leaves no queued request. A hard refusal is spooled to the owning daemon's `<run>/host-alerts` (the shim policy's `alert_spool`, or the `--instance`'s spool when it exists), which raises it as a host-admission alert (FAE-HOST-003). With `--shim-policy FILE` the weight, class and ledger come from the role shim policy (above) and explicit `--weight/--class/--ledger` are a usage error.
